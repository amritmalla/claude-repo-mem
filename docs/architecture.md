# Architecture

This document explains how `claude-repo-mem` turns a repository into queryable
memory. It is written for contributors; for how to *use* the tools, see
[usage.md](usage.md) and [tools.md](tools.md).

## Overview

```
files ──▶ walker ──▶ parsers ──▶ synthesizers ──▶ summarizer ──▶ DB (SQLite + sqlite-vec)
                                                                      │
                                          recall / trace / expand ◀───┘
```

Everything is local-first. State lives in a single `.claude-repo-mem/` directory
at the repo root (see [State directory](#state-directory)). Indexing populates a
SQLite database of **units** (chunks of code, docs, memories, tasks) and
**relations** (edges between them). Retrieval reads from that database.

## Indexing pipeline

The pipeline is orchestrated by `indexer/orchestrator.py` (full reindex) and
`indexer/incremental.py` (incremental updates).

### 1. Walker — `indexer/walker.py`

Discovers candidate files under the repo root, applying ignore rules so build
artifacts and vendored code don't pollute the index.

### 2. Parsers — `indexer/parsers/`

Each file is parsed into units at natural boundaries. Code parsers are
tree-sitter based, one module per language:

| Language | Parser | Units |
|----------|--------|-------|
| Python | `code_python.py` | classes, methods, functions, docstrings |
| JavaScript / TypeScript | `code_jsts.py` | functions, classes, methods, JSX |
| Java | `code_java.py` | classes, interfaces, methods, constructors |
| Go | `code_go.py` | funcs, methods, structs, interfaces |
| Rust | `code_rust.py` | fn, impl methods, structs, traits |
| Markdown | `markdown.py` | sections by heading hierarchy |
| `memory.md` | `memory_md.py` | durable memory entries |

`parsers/base.py` defines the parser interface.

### 3. Synthesizers — `indexer/synthesizers/`

Synthesizers add cross-file relation edges on top of parser output. Each targets a
framework or language convention:

- `flask_routes.py` — `@app.route(...)` → handler
- `django_urls.py` — `path(...)` / `re_path(...)` → handler (resolves dotted refs
  against `views.py`)
- `express_routes.py` — `app.METHOD(url, handler)` → same-file handler
- `imports.py` — Python imports → cross-module edges
- `react_hooks.py` — `useState` setter calls → `mutates_state_of` edges on the
  containing component

These edges are what `trace` walks at query time.

### 4. Summarizer — `summarizer/`

Units are stored at multiple tiers. `T1` (header) comes straight from the parser.
`T2` (summary) is generated by an LLM and backfilled (`summarizer/backfill.py`),
which is why a fresh index may show partial `t2_coverage` in `doctor` until
summarization catches up. `T0` is the full source/content.

## Storage — `db/`

- `db/connection.py` — opens the SQLite connection and loads the `sqlite-vec`
  extension for vector search.
- `db/schema.py` — defines the schema: a `unit` table, a `relation` table, an FTS
  index for lexical search, and a vector table for embeddings.
- `db/repository.py` — typed read/write access over the schema (`Repository`,
  `get_unit`, row mapping).

Units carry a **layer** — one of `memory`, `docs`, `code`, `task` (enforced by a
schema `CHECK` constraint). Layers are how retrieval and the `tasks`/memory tools
partition the store; finer distinctions (e.g. a task snapshot) are carried in the
unit's `kind` (`task_snapshot` is a kind within the `task` layer). Superseded units
are marked via `superseded_by` rather than deleted.

## Retrieval — `retrieval/`

### recall — `retrieval/recall.py`

Hybrid retrieval: lexical (FTS) and vector (embedding similarity via sqlite-vec)
candidates are merged and ranked (`retrieval/ranker.py`), then `retrieval/fill.py`
fills results into the token budget across tiers — full content (T0) for the top
hits, summaries (T2) for the mid-tier, headers (T1) for the tail. Anything that
doesn't fit is returned as `overflow_handles`.

### trace — `retrieval/trace.py`

Breadth-first traversal from seed handles over the relation graph (capped at depth
3), optionally filtered by relation kind, returning full source for connected
units within a budget. This is the one-shot alternative to repeated `expand`
calls.

## Embeddings — `embeddings/`

Pluggable embedders behind `embeddings/base.py`, selected by
`embeddings/factory.py`:

| Backend | Module | Notes |
|---------|--------|-------|
| `bge-small` (default) | `bge_small.py` | `BAAI/bge-small-en-v1.5`, 384-dim, local CPU, no API key |
| `openai` | `openai_emb.py` | requires `OPENAI_API_KEY` |
| `voyage` | `voyage_emb.py` | requires `VOYAGE_API_KEY`, 512-dim |

Selection is via the `CLAUDE_REPO_MEM_EMBEDDER` env var or the `--embedder` flag on
`index`.

## LLM backends — `llm/`

Summarization and `plan_task` need an LLM, selected by `llm/factory.py` via
`CLAUDE_REPO_MEM_LLM`:

- `mcp` (default) — `mcp_sampling.py`, asks the MCP host (Claude Code) to sample.
  No API key needed; only works inside an MCP session.
- `anthropic` — `anthropic_api.py`, direct Anthropic API; requires
  `ANTHROPIC_API_KEY`.

## Incremental updates and the watcher

`indexer/incremental.py` re-indexes only changed files. When `serve --watch` is
on, a `watchdog`-based file watcher feeds changes through a debounced background
queue (`queue/background.py`, 750ms) so the index tracks edits live. As an
alternative to the watcher, `install-hooks` writes a git `post-commit` hook that
re-indexes on commit.

## Distill and handoff

- `distill/` — extracts durable memory candidates from a Claude transcript
  (`transcript.py` → `extract.py` → `confirm.py`), surfaced via the `distill` CLI
  command.
- `handoff/` — `snapshot.py` renders a task to markdown under
  `.claude-repo-mem/handoffs/`; `resume.py` rehydrates it; `render.py` formats the
  snapshot. These back the `handoff` and `resume` tools.

## Observability — `observability/`

`counters.py` tracks per-tool call counts, surfaced through the `stats` tool and
the `doctor` CLI command.

## State directory

Everything persistent lives under `.claude-repo-mem/` at the repo root (see
`config.py`):

| Path | Contents |
|------|----------|
| `db.sqlite` | the unit/relation index and vectors |
| `blobs/` | stored content blobs |
| `handoffs/` | task handoff snapshots (markdown) |
| `memory/` | durable memory entries (`<scope>/<slug>.md`) |
| `scopes.yml` | scope configuration |

The root is resolved by `Settings.discover()` — walking up from the cwd looking
for a `.claude-repo-mem/` directory — or pinned explicitly with `--root`.
